# 도구를 연결해서 쓰는 법

처음 사용하는 분은 [빠른 시작](../README.md#빠른-시작)에서 연결한 뒤 회사와 질문을 말하면 됩니다.
이 문서는 AI 에이전트나 대시보드를 연결하는 개발자가 **무엇을 호출하고, 결과를 어떻게 읽고,
언제 멈출지** 확인하는 안내입니다. 입력 이름과 허용값의 정본은 [도구별 문서](../wiki/tools/README.md)와
연결한 서버의 `tools/list`입니다.

## 가장 짧은 분석 흐름

1. **대상과 기준일을 정합니다.** 회사별 질문은 `company`로 회사를 찾습니다. 시장 전체 질문은
   `screener`나 해당 도구의 시장 조회 기능으로 시작합니다. 회사 검색 실패를 시장 전체 조회로 바꾸지 않습니다.
2. **질문에 필요한 범위만 읽습니다.** 요약에서 공시 접수번호를 얻고, 후보·임기·출석 등 필요한 상세만
   이어 읽습니다. 이미 받은 자료를 같은 조건으로 다시 요청하지 않습니다.
3. **상태와 근거를 먼저 확인합니다.** 부분 응답, 해석 후보, 잘린 원문, 기준이 다른 수치를 구분합니다.
4. **답과 확인이 필요한 항목을 함께 제시합니다.** 읽지 못한 값은 미상으로 두고, 출처와 다음 조회 경로를 붙입니다.

아래의 `분석할 회사명`과 `확정된 고유번호`는 입력 자리표시자입니다. 실제 회사명이나 앞 단계에서
반환된 식별자로 바꿔야 합니다. 종목코드·고유번호·접수번호는 앞자리 영을 보존하는 문자열입니다.

```json
{"name":"company","arguments":{"query":"분석할 회사명","max_recent_filings":3,"format":"json"}}
```

회사가 확정되면 반환된 `data.identifiers.corp_code`를 다음 도구의 **`company` 인자**에 넣습니다.
모든 도구에 `corp_code`라는 인자가 따로 있는 것은 아닙니다. `company` 검색의 `ambiguous` 응답은
후보를 고르기 전까지 다음 호출로 넘기지 않습니다. `exact`라도 자동 추론이면 해석 근거와 대안을 확인합니다.

```json
{"name":"director_board","arguments":{"company":"확정된 고유번호","scope":"roster","lookback_years":3,"format":"json"}}
```

## 질문별 연결 순서

| 알고 싶은 것 | 첫 조회 | 필요한 경우 이어서 | 혼동하지 말 것 |
|---|---|---|---|
| 현재 이사·감사와 재직 변화 | `director_board`, `scope="roster"` | 같은 회사의 소집공고 `scope="board"`, 주총 결과, 원문 각주 | 재직 중인 사람·선임 후보·선임이 의결된 사람은 서로 다른 상태 |
| 다가오는 주총의 후보 | `shareholder_meeting_notice`, `scope="summary"` | 같은 접수번호로 `scope="board"` | 후보를 현재 재직자로 단정하지 않기 |
| 임기 만료가 가까운 감사 | 명부의 임기 원문과 보고 기준일 | 정정·임시주총·중도퇴임 공시와 대조 | 감사·감사위원·외부 회계감사인 구분; 기간만으로 만료일을 확정하지 않기 |
| 주총 결과와 찬반율 | `shareholder_meeting_results` | 해당 회차의 소집공고, 근거 원문 | 가결 여부와 찬성률 구분; 발행주식·의결권주식·행사주식의 분모 구분 |
| 의결권 검토 | `proxy_advise_before_meeting` | 반환된 누락 근거에 해당하는 도구, `proxy_guideline`, `law_lookup` | 정책·원문·AI 해석·사람 검토 여부를 분리 |
| 오늘 달라진 공시 | `screener`로 기간·대상 지정 | 필요한 공시만 상세 조회 | 오늘 발생한 사건과 과거 사건의 오늘 정정공시 구분 |
| 자산·가치평가 | `asset_holdings`, `price_multiple_data` | 재무와 보유지분 근거 | 장부가·시가·연결/별도·기준일을 유지; 겹치는 자산 중복 합산 금지 |

접수번호를 받은 소집공고는 `rcept_no`를 지정해 같은 회차를 이어 읽을 수 있습니다.
도구에 없는 `cursor`, `offset`, `scope="all"`을 만들어 보내지 않습니다. 원문 확대·후보 재검색·계속 읽기
방법은 해당 도구가 실제 반환한 안내와 스키마를 따릅니다. `evidence`는 접수번호를 원문 링크로 연결하는
도구이지, 모든 문서의 전체 본문을 읽는 범용 페이지 도구는 아닙니다.

## 응답을 읽고 다음 행동을 고르기

통신 성공과 분석 성공은 다릅니다. MCP의 `isError`를 확인한 뒤 본문의 `status`, `warnings`,
`data.error_kind`와 `data.retry`가 있으면 함께 읽습니다. 오류 응답도 정상적인 MCP 응답 봉투에
담길 수 있습니다. `format="json"`은 지원하는 도구에만 지정하며, JSON이 텍스트 콘텐츠에 들어오는
현재 응답과 MCP 자체 오류를 구분합니다.

| 받은 결과 | 다음 행동 |
|---|---|
| 회사 후보가 여러 개 | 회사명·종목코드로 대상을 확정한 뒤 재조회 |
| `partial`, `requires_review`, `conflict` 또는 누락 경고 | 확보한 부분은 답하고, 누락·상충한 항목만 추가 확인 |
| 자료 없음·원문 없음 | 조회 범위와 공시 종류를 확인; 같은 요청 무한 반복 금지; 없음과 숫자 영을 구분 |
| 잘린 원문·추가 후보 | 반환된 확대 방법을 적용하고 읽은 범위를 표시; 잘린 부분에 답이 없다고 단정하지 않기 |
| 키 오류·접근 차단 | 해당 수집을 멈추고 키 상태 또는 운영 상태 확인; 키를 채팅에 요청하거나 출력하지 않기 |
| 한도 초과 | 해당 수집을 멈추고 재개 시점과 배치를 조정; 다른 키·프로세스로 우회하지 않기 |
| 일시적 지연·상류 장애 | 재시도 가능한 경우에만 제한된 횟수와 대기 간격 적용; 소진되면 실패를 표시 |
| 내부 오류·유효하지 않은 입력 | 같은 입력을 반복하지 말고 도구명·민감정보를 뺀 입력·오류 종류로 재현 |

배치 호출의 대기·동시성·총 호출 예산은 호출자가 관리합니다. 제한 수치는 [운영 경계](ARCHITECTURE.md#operational-boundaries)를
따릅니다. 도구 호출 한 번이 외부 API 한 번을 의미하지 않습니다. 현재 내부 호출계수는 JSON 요청을 세지만
문서 ZIP 요청까지 전부 세지는 않으므로, 표시된 호출 수만으로 총 외부 요청 예산을 보장하지 않습니다.
수집기는 문서 요청·캐시 재사용·실패를 따로 기록하고 보수적인 상한을 둡니다.
회사·기간·접수번호·요청 범위와 완료 여부로 재개 지점을 관리하고 실패 항목만 다시 처리합니다.

## 결과를 표나 대시보드에 옮길 때

숫자 옆의 단위·통화·연결/별도·대상 기간·공개일·확정/잠정/예상 구분을 함께 전달합니다.
이름·역할·임기를 정규화해도 원문 표현과 근거 접수번호를 남깁니다. 서로 다른 사람이 같은 이름을 쓰거나
동일인이 여러 역할을 맡을 수 있으므로 이름만으로 합치지 않습니다. 불명확한 날짜는 확정 날짜 필터에 넣지 않습니다.

사용자 조회 결과는 서버에 저장하지 않는 것이 기본입니다. 지속적인 서비스용 수집은 사용자 대화 기록과
분리된 시장 스냅샷·원문 캐시·검증 절차로 운영해야 합니다. 데이터 수집 성공, 파싱 성공, 근거 확인,
최신성은 서로 다른 상태로 표시합니다.

## 변경 후 확인

문서와 등록된 입력이 맞는지 카탈로그 검사를 하고, 파싱 수정은 고정된 원문 캐시로 전후를 비교합니다.
사용자가 보는 출력은 로컬 MCP 서버를 실제 호출해서 확인합니다. 내부 함수 테스트 통과만으로
통신·입력 검증·렌더링까지 확인했다고 쓰지 않습니다. 배포 후에는 같은 핵심 경로를 운영 서버에서 확인합니다.

로컬 호출 도구는 `scripts/mcp_probe.py`입니다. 현재 이 도구의 종료 코드만으로 분석 성공을 판정하지 마세요.
`isError`와 본문 상태를 엄격히 검증하는 게이트는 별도 보강 대상입니다.
