# MCP 요청·응답 검증

MCP는 모델과 도구가 요청·응답을 주고받는 인터페이스다. 내부 함수의 반환값만 맞아도 이 경로는 실패할 수 있다.
대상 `CLAUDE.md`와 [공통 근거 계약](../opm-tool-validation/references/evidence.md)을 읽는다.

## 검증 수준을 먼저 선택

| 수준 | 경로 | 입증하지 않는 것 |
|---|---|---|
| 앱 내부 | 실제 `build_app()`에 테스트 클라이언트로 MCP HTTP 요청 | 별도 프로세스·네트워크·배포 설정 |
| pilot | 승인된 로컬 서버에 streamable-http 요청 | 운영 배포 |
| live | 별도 승인된 운영 서버의 제한된 확인 | 시장 전체 정확도 |

앱 내부 검사는 네트워크 없이 시작한다. 원천 응답만 고정하고 실제 도구 등록·wrapper·service·렌더러는 지나간다.
기존 service/payload/renderer를 mock한 성공을 전체 도구 성공으로 세지 않는다.
pilot/live는 과업 범위와 외부 호출 예산을 확인한다. 스킬 선택은 서버 배포나 실데이터 수집의 승인이 아니다.

## 절차

- 실제 도구 목록과 입력 계약을 확인하고 필요한 도구, scope, 연도, 식별자, 출력 형식을 고정한다.
- 요청 흐름은 대체로 발견 → 입력 확인 → 좁은 호출 → 필요한 경우에만 확장이다.
  검색 필터·원문 위치·다음 경로를 사용하고 같은 넓은 호출을 오류 뒤 무한 반복하지 않는다.
- 성공 경로뿐 아니라 알 수 없는 도구, 잘못된 인자, 빈 데이터, 상위 응답 오류, 부분 데이터,
  검토필요 상태와 경고를 시험한다. 빈 결과를 `0`이나 `전원 이탈` 같은 확정 사실로 오해하지 않게 한다.
- HTTP 성공만 보지 않는다. JSON-RPC 오류, 도구의 `isError`, content 형식·비어 있음,
  구조화 데이터, 사람이 읽는 출력의 경고·출처까지 확인한다.
- 도구 설명의 인자와 실제 허용 인자가 맞는지, 필요한 선택자·scope가 전달되는지 검사한다.
  출력 형식이 JSON과 Markdown이면 양쪽에서 같은 대상·기간·상태가 유지되어야 한다.
- mock 경계와 차단된 네트워크 시도를 기록한다. 앱 내부 이벤트 루프 통신과 외부 접속은 구분한다.
- 실행 경로·명령은 [연결된 검사](../opm-tool-validation/references/commands.md)를 따른다.

## 통과 조건

요청부터 사용자 응답까지 해당 계약이 확인되고 실패·불확실성도 올바르게 전달되어야 PASS다.
`build_*_payload` 직접 호출만 했다면 MCP 단계는 NOT_RUN이다.
앱 내부 테스트만 통과했다면 pilot/live는 NOT_RUN으로 남긴다. 운영 점검 때문에 배포하지 않는다.
